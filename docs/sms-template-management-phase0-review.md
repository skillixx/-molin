产品规则：五个场景分别使用独立模板；模板只使用审核通过的 `${code}` 变量；同一场景同一时刻只有一个当前绑定；`accepted` 或阿里云 `Code=OK` 只表示供应商受理，不表示运营商送达或用户已收到。首期无回执，因此不提供送达率产品承诺。

### 2.2 签名与测试发送

- 首期只使用一个由阿里云审核通过的墨灵品牌签名。
- 模板申请时展示的“关联签名”只用于辅助审核，不作为实际发送的强绑定；运行时统一以 `SendSms.SignName=SMS_ALIYUN_SIGN_NAME` 为准，但该固定签名自身必须审核通过、场景相符且满足实名报备要求。
- 签名来自安全配置或后端已审核来源，管理后台只读展示，不允许自由输入。
- 测试发送的模板必须审核通过、本地启用，并与请求 `scene` 的当前已启用绑定一致；绑定停用时不得提交。
- 测试发送必须使用 `Idempotency-Key`。相同管理员、模板、场景、手机号身份和 key 的重试返回首次结果，不重复提交；相同 key 修改参数返回 `409/40900`。
- 前端按钮禁用和后端限流仍须保留，但不能替代幂等键。

## 3. 阶段时序修正

原规划在阶段 1 要求读取场景绑定并写发送状态，却把相关 migration 全部放到阶段 2，无法实施或验收。现修正为：

```text
阶段 0
  → 批准最小 migration、配置、数据库唯一权威和正式契约
阶段 1
  → 迁移 verification_codes 和三张短信最小可用表
  → 建立仓储、阿里云适配器和关闭态业务链路
  → 使用数据库 fixture + Mock 验证 pending → accepted/failed，不发送真实短信
阶段 2
  → 先开放阿里云同步和场景绑定 API
  → 受控建立五场景数据库绑定
  → 完成其他管理 API 和真实短信验证
阶段 3
  → 前端按已合并契约开发
```

阶段 1 最小 migration 必须解决验证码 SHA-256 十六进制哈希需要 64 字符而当前模型长度不足的问题，并明确历史记录、邮箱记录以及手机新记录的不同校验策略；同时创建 `sms_templates`、`sms_scene_bindings`、`sms_send_logs` 最小可用表和仓储。邮箱不得调用短信适配器；手机短信失败记录不得通过验证码校验。模板编码禁止进入环境变量，阿里云同步快照和数据库绑定是唯一权威。
