# 阿里云短信验证码阶段 2 部署、监控与回滚说明

## 发布前门禁

1. PR 已通过 Linux CI：`go mod verify`、`go vet ./...`、`go test -race -count=1 ./...`，其中 MySQL 8 完整矩阵真实执行而非 SKIP。
2. 测试工程师与产品经理已经签署阶段 2 通过，P0/P1 未关闭缺陷为 0。
3. 已完成数据库备份并记录恢复点；确认 migration `000059` 的 up/down/up 证据。
4. RAM 仅具有模板读取和短信提交所需最小权限，AccessKey 只通过安全环境变量或 Secret Manager 注入。
5. `SMS_ENABLED=false`、`SMS_TEST_MODE=true`、白名单非空且总预算不超过 500 条。
6. 真实发送、测试服务器改动、部署、远程 Git 和短信费用必须分别取得项目负责人明确授权。

## 部署顺序

1. 部署兼容阶段 2 的 API 二进制，但保持 `SMS_ENABLED=false`。
2. 在已备份的目标环境执行 migration `000059`，核对四权限、admin 绑定、同步锁及新增索引。
3. 以管理 API 只读同步模板；禁止通过人工 SQL 配置正式场景。
4. 通过管理 API 为五场景逐项绑定审核通过且本地启用的模板。
5. 在单独授权窗口内设置 `SMS_TEST_MODE=true` 和白名单，再临时开启 `SMS_ENABLED=true`。
6. 按“模板同步 → 单次测试提交 → 五业务入口”执行验证，分别记录本地调用、阿里云受理和手机实际收件。
7. 验证结束立即恢复 `SMS_ENABLED=false`；未经产品经理放量批准不得再次开启。

## 监控指标与告警

| 观察项 | 要求 |
|---|---|
| 供应商受理/失败计数 | 按 `accepted/failed` 统计，不把 accepted 命名为送达成功 |
| 供应商安全错误类别 | 观察 timeout、rate_limit、signature、template、arrears、network、rejected，不记录原始响应 |
| API 状态 | 观察 400/401/403/409/429/502/503 比例和请求耗时 |
| 模板同步 | 观察最后同步时间、创建/更新/忽略计数及连续失败 |
| 场景配置 | 五场景都应只有一个有效绑定，模板审核失效后不得继续发送 |
| 测试发送 | 观察管理员/手机号 HMAC 双维限流、幂等冲突和 pending 是否长期不收敛 |
| 安全审计 | 同步、绑定、启停、测试发送四类动作必须可追溯，且无号码、验证码、Token 或密钥 |

建议告警：连续 5 分钟供应商失败比例超过 20% 且样本不少于 10、任一签名/模板/欠费错误、模板同步连续失败、测试发送出现长期 pending，均应保持或恢复 `SMS_ENABLED=false` 并由人工诊断。

## 应用回滚

1. 首先将 `SMS_ENABLED=false`，验证五个手机发码入口均失败关闭且不生成可校验验证码。
2. 停止继续执行模板同步、绑定、启停和测试发送写操作。
3. 回滚到上一版 API 二进制；阶段 1 代码会忽略阶段 2 新增列，但仍须保持短信关闭。
4. 核对邮件验证码链路、健康检查、审计和日志没有回归。

## 数据库回滚

数据库回滚不是普通故障处理的第一选择，只能在已备份、应用已回滚且短信关闭后执行：

1. 确认阶段 2 新增权限没有被其他角色、用户覆盖或分组引用；down migration 会对此失败关闭。
2. 执行 `000059` down，核对阶段 1 的 `sms_templates/sms_scene_bindings/sms_send_logs` 仍存在，`verification_codes` 的统一安全字段未变化。
3. 若 down 因未知权限引用失败，不得绕过保护或手工删除；恢复阶段 2 应用并先处理引用关系。
4. 必要时使用发布前恢复点恢复数据库，并重新核对邮件、短信关闭态和权限数据。

禁止执行 `DROP DATABASE`、`TRUNCATE`、批量删除发送记录或清空 Redis。任何数据删除和生产数据库恢复都需要额外明确授权。
