# 阿里云短信验证码阶段 5 反向代理核验报告

## 1. 仓库静态结果

`python infra/nginx/verify_forwarded_headers.py` 已通过。`admin.conf`、`user.conf`、`api.conf` 的 API 反代均：

- 覆盖 `X-Real-IP $remote_addr`；
- 删除 `X-Forwarded-For`；
- 删除 `Forwarded`；
- 不使用 `$proxy_add_x_forwarded_for`；
- 对一次性内部 bootstrap 路径保持公开 404。

## 2. 测试服实际结果

管理端和用户端运行中 Nginx 配置均包含上述三条来源头指令，API 健康为 200。两容器当前位于 Docker 默认
bridge 子网 `172.17.0.0/16`，通过 `172.17.0.1:8080` 访问宿主机 API。

## 3. 未通过项

API 进程 `TRUSTED_PROXY_IPS` 为空。Nginx 虽正确覆盖来源头，应用仍不会采用该值。结论：**Nginx 配置通过，
端到端可信代理链未通过。**

只读网络盘点显示当前主机已使用 `100.93.0.0/16`、`172.17.0.0/16`、`172.18.0.0/16`、
`172.19.0.0/16`、`172.31.250.0/24` 和 `192.168.29.0/24`。当前候选专用网络为
`172.20.250.0/28`，规划管理端 `172.20.250.2`、用户端 `172.20.250.3`，目标
`TRUSTED_PROXY_IPS=172.20.250.0/28`。该候选仅为当前快照下的计划，正式创建前必须重新读取路由和全部
Docker 网络；发现重叠即停止，不得自动换到更宽网段。

`scripts/verify-sms-phase5-proxy-network-plan.ps1 -SelfTest` 已证明当前候选通过、与 `172.17.0.0/16`
重叠的反例失败关闭；脚本本身不连接远端、不创建网络、不写配置、不重启服务。

## 4. 部署态验收矩阵

| 场景 | 期望 |
|---|---|
| 非可信直连伪造 XFF/X-Real-IP | 忽略伪造头，只按 `RemoteAddr` |
| 可信代理 + 一个合法 X-Real-IP | 使用该值作为最终来源 |
| 可信代理缺失 X-Real-IP | 403/40003，业务与供应商调用增量 0 |
| 可信代理重复/逗号多值/非法 X-Real-IP | 403/40003，业务与供应商调用增量 0 |
| 合法 X-Real-IP + 冲突 XFF/Forwarded | 只采用 X-Real-IP |
| 轮换伪造转发头 | 不能绕过第 11 次 IP 限流 |

以上动态矩阵尚未执行，必须在修复测试服可信代理配置并取得重启/测试授权后完成。
