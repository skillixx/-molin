# AI 网关 G5 测试环境部署与回滚手册

## 使用边界

本文仅用于墨灵远程测试环境。生产环境、真实客户流量和付费上游放量不在 G5 验收范围内。部署期间必须保持 `SMS_ENABLED=false`，不得在命令、日志或验收文档中输出 SK、数据库密码或 JWT。

## 部署前门禁

1. 确认 PR 已合并、CI 全绿，部署提交包含最新 `origin/main`，工作树无未确认修改。
2. 记录当前应用镜像或二进制版本、前端静态包版本、数据库 `schema_migrations` 版本和容器健康状态。
3. 创建数据库备份并验证备份文件非空；记录恢复命令但不得把凭据写入仓库。
4. 检查磁盘、MySQL 活跃长事务、metadata lock、`token_models` 与 `token_channels` 行数。存在长事务或锁等待时终止本次部署并排查。
5. 维护窗口内暂停新 AI 网关流量；短信、订单和钱包等非网关服务保持原配置，不得顺带变更。

## Migration 64

1. 使用项目固定的 `migrate/migrate:v4.18.3` 和正式数据库连接执行 `up 1`。
2. Migration 设置 10 秒锁等待上限；锁超时属于可重试失败，先恢复 AI 网关流量，再清理长事务并重新安排窗口，不得无限重试。
3. 只读确认版本为 `64:0`，四张 G5 表、模型与渠道新增字段、15 个命名约束均存在。
4. 确认模型发布、路由、价格和安全审计事实表为空或符合预期，不执行清表。

### dirty 或部分 DDL 恢复

1. 一旦 Migration 失败，立即停止后续部署，读取 `schema_migrations.version/dirty`，并逐项核对 000064 的字段、四张表和 15 个命名约束；不得直接再次执行 `up`，也不得盲目执行 `force`。
2. 若版本仍为 `63:0`，确认没有任何 000064 DDL 落地后，才允许清理锁并在新窗口重跑。若已有部分 DDL，因 000064 可重入，应由两名审查人确认现状与脚本条件分支一致后再处理版本状态。
3. 仅当部分 DDL 与 000064 目标完全一致、备份可用且审查记录完整时，才允许使用 `migrate force 63` 清除 dirty 标记并重新执行 `up 1`。`force` 只改版本状态，不会补执行 DDL。
4. 若部分 DDL 不一致或无法证明一致，保持网关停流，使用部署前备份恢复数据库；恢复后验证版本、核心表行数、钱包与消费事实，再重新安排部署。

## 应用部署

1. 部署与合并提交一致的 Go 服务和管理后台静态包，保留上一版本制品。
2. 验证 `/api/health`、`/api/ready`、`/api/version`，并确认 `SMS_ENABLED=false`。
3. 使用测试管理员验证 G5 工作台读取、权限隔离和错误反馈；不得使用真实用户凭据。
4. 使用最低成本模型执行一次真实 Bifrost 请求，核对 request、route attempt、usage、provider cost、人民币结算、钱包单笔消费和工作台汇总。

## 回滚

1. Migration 64 的 down 为审计保护型 no-op，不删除字段和事实。应用异常时先停 AI 网关入口，回滚 Go 服务和管理后台到部署前制品。
2. 验证旧应用可在 schema 64 上启动并通过健康检查，再恢复流量；若不兼容，保持网关停流并按备份恢复数据库，不直接手工删除字段或事实表。
3. 对已进入结算链路的请求按 request id 核对幂等事实，不重复扣费；记录失败时间、提交、Migration 版本和恢复结果。
4. 回滚后重新验证短信关闭状态、钱包余额、消费流水和非网关核心接口，确保没有共享服务回退。

## 验收证据

保存但不提交敏感原文：PR/CI 链接、部署提交、备份校验值、Migration 前后版本、健康检查、真实 Bifrost request id（脱敏）、计量与钱包对账、三宽度 UI 截图、QA 和产品确认结论。P0/P1 不为零时不得标记 G5 完成。
