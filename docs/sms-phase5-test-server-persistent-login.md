# 阶段 5 测试服验证码登录长期放行说明

## 目标与当前状态

目标是在固定测试服长期提供手机验证码登录，同时继续限制真实短信的号码和业务场景。代码与本地测试完成不代表测试服已经开启；测试服配置修改、后端发布、服务重启和真实短信费用仍需单独批准并取得执行证据。

## 固定安全边界

- `SMS_ENABLED=true`：允许登录页面按用户操作提交真实短信。
- `SMS_TEST_MODE=true`：持续启用测试隔离，不进入生产全量模式。
- `SMS_TEST_SCENE_ALLOWLIST=login`：只允许登录场景，注册、找回密码、换绑手机和管理员二次认证短信全部失败关闭。
- `SMS_TEST_PHONE_WHITELIST`：保留当前两个已批准自有号码，不在代码、候选、日志或文档中保存完整号码。
- 同一手机号与 `login` 场景 60 秒内只允许一次供应商提交；接口 IP 限流继续生效。
- 不提供自动重试；供应商受理不等于最终送达，每次用户主动发码都可能产生供应商费用。

## 代码门禁

API 启动时必须校验测试场景白名单非空、无未知场景且无重复场景。Dispatcher 在模板查询前同时检查场景白名单和手机号白名单，因此未放行场景不会创建 OTP、不会新增发送日志，也不会调用阿里云。

## 测试服发布与回滚

测试服现有二进制不具备场景白名单能力，禁止只把原配置的 `SMS_ENABLED` 改为 `true`。正确顺序为：

1. 构建并核验包含本门禁的新后端二进制。
2. 保存当前二进制、环境文件和进程环境的精确恢复材料。
3. 将环境文件精确设置为 `SMS_ENABLED=true`、`SMS_TEST_MODE=true`、`SMS_TEST_SCENE_ALLOWLIST=login`，保留原手机号白名单。
4. 原子切换二进制并受控启动 API，核验唯一 PID、二进制摘要、进程环境、`health` 和 `ready`。
5. 失败时自动恢复原二进制、原环境文件和原进程环境，并保持 `SMS_ENABLED=false`。

主动关闭或异常止损时先将 `SMS_ENABLED=false`，再受控重启 API；不得删除发送日志、OTP 记录或监控证据。

## 启用前监控硬门禁

长期真实短信不能在 Alertmanager `discard` 状态下无人值守运行。正式启用前必须二选一并记录责任人：

- 恢复已经完成单次演练的邮件通知路由，允许实际运行异常时发送运维告警邮件；或
- 明确观察人、只读巡检频率、费用检查频率和触发停止线后的关闭 SLA。

未取得邮件告警授权且未形成可执行人工值守方案时，长期启用候选必须失败关闭。当前测试服仍为 `discard`，因此本项尚未通过。

## 验收

- 白名单内已注册账号可请求 `login` 验证码并完成一次验证码登录。
- 白名单外手机号以及 `register`、`reset_password`、`bind_phone`、`admin_verify` 均被拒绝，供应商调用增量为零。
- 日志、接口响应和部署结果不出现完整手机号、验证码、Token 或阿里云密钥。
- 停止线包括供应商失败率异常、费用异常、健康检查失败、非登录场景出现供应商调用或白名单外号码被受理。
