# 阿里云短信验证码阶段 2 测试报告

## 结论

截至提交 `34b69a4`，阶段 2 后端实现、本地自动化、MySQL 8/Redis 7/Linux race CI、隔离测试服部署、模板同步、五场景绑定和受控真实短信验证均已形成证据。PR #315 当前提交对应的 [GitHub Actions 运行 #375](https://github.com/skillixx/-molin/actions/runs/30820296650) 三项任务全部通过。

隔离测试服已部署 `34b69a4`，数据库为 `59:0`。真实窗口共形成 7 条阿里云 `Code=OK`/`accepted` 记录：1 条管理测试发送、6 条 OTP；其中包含一次因本地进程停止超时而未继续换绑流程的额外 `bind_phone` 受理记录。阶段要求的 1 次测试发送和 `register/login/reset_password/bind_phone/admin_verify` 五入口均已受理。用户确认最后四条短信的收件分布为“原白名单手机号 3 条、新绑定管理员手机号 1 条”；此前 `bind_phone`、`admin_verify` 验证码均已被成功消费，分别完成管理员 259 换绑真实手机号和手机 MFA 验证，构成实际收件证据。

验证结束后已恢复 `SMS_ENABLED=false`、`SMS_TEST_MODE=true` 和原白名单（1 个号码）。运行时脱敏扫描通过，未发现完整手机号、验证码明文、AccessKey、Bearer Token 或 JWT 泄露。但真实同步只有 1 个合格模板，五场景全部绑定该模板，违反“五场景分别使用独立模板、不得用含糊文案覆盖全部用途”的产品规则。独立 QA 和产品经理均给出不通过结论，PR #315 不得合并，也不得进入阶段 3。

针对该验收缺口，当前开发分支已增加后端防回归约束：同一模板不得绑定到多个启用场景，两个场景并发争用同一模板时只能一个成功；历史共用绑定仍允许停用，以便逐项整改。该代码仅完成本地定向自动化验证，尚未部署，也不能替代阿里云补齐五个独立审核模板、重新绑定及 QA/PM 复验。

## 真实验证计数与口径

- `sms_send_log_total=7`，`accepted=7`，`provider_code=OK` 为 7。
- 用途分布：`test=1`、`otp=6`。
- 场景分布：`admin_verify=1`、`bind_phone=2`、`login=1`、`register=2`、`reset_password=1`。
- 阶段要求的六项证据为“管理测试发送 1 次 + 五业务入口各 1 次”。额外的一次 `bind_phone` 受理只作为异常恢复记录，不重复计入入口验收。
- 7 次受理均可能产生计费，数量低于 500 条预算；本报告不虚构实际账单金额。
- `accepted` 仅证明阿里云受理；实际收件依据为用户确认或验证码成功消费，不把 `Code=OK` 冒充送达证明。
