## 四、缺陷 #1 复测结果：**已修复，验证通过 ✅**

**复现步骤（与首轮完全一致）**：
1. 注册一个全新账号（**全程不调用 `GET /api/wallet`，不发起任何充值**）
2. 通过管理员将其实名状态置为 `verified` 并分配具备 `can_buy` 权限的角色
3. 直接调用 `POST /api/products/{id}/purchase`（带合法 `Idempotency-Key`）

**首轮实际结果**：`HTTP 500 {"code":50000,"message":"record not found","data":null}`

**本轮实际结果**：

```
已注册全新账号 user_id=24（未调用 /api/wallet、未充值）
PASS  全新用户首次购买在余额不足场景下正确返回 400/60001（钱包懒创建链路无异常）
```

返回 `HTTP 400 {"code":60001}`（余额不足），与期望结果完全一致。

**结论**：缺陷 #1【P1】全新用户首次购买触发 HTTP 500 **已修复，验证通过**。
修复方案（在 `deductOnce`/`DeductTx`/`Freeze` 中捕获 `gorm.ErrRecordNotFound` 并转换为
`ErrInsufficientBalance`）符合首轮报告中的修复建议，"钱包不存在等价于余额为 0"
的语义在代码层面得到统一处理，影响所有"从未访问过钱包页面、未充值过的新用户首次购买"
的阻断性问题已消除。

## 六、缺陷 #2 当前状态确认：**保持不变（未修复，等待产品经理决策）**

**复现步骤（与首轮完全一致）**：
1. 创建一个商品，配置默认价 `20.00` + 会员专属价（`membership_level_id=qa_gold`）`6.00`
2. 创建账号 A（VIP 会员，含有效 `user_memberships` 记录）和账号 B（非会员，无该记录），
   分配相同购买角色，实名认证通过、余额充足
3. 分别用 A、B 两个账号下单购买该商品

**本轮实际结果**：

```
PASS  VIP 用户购买会员价应用 → 按会员价 6.00 扣费（实际扣减=6）
非会员下单返回：HTTP 200, amount=20，按非会员价正常成交，未受任何拦截
FAIL  非会员无法购买会员专属应用（业务规则缺失）
      当前购买访问控制仅基于角色 product_role_access.can_buy，不存在与
      membership_level 绑定的"会员专属"购买门槛；非会员账号成功完成购买
      （HTTP 200），未被拦截。
```

- 账号 A（VIP）：`HTTP 200, amount=6` —— 符合预期（会员价定价隔离正常）
- 账号 B（非会员）：`HTTP 200, amount=20` —— **仍未被拦截，按默认价正常成交**

**结论**：缺陷 #2【P1/设计缺口】"非会员无法购买会员专属应用"业务规则**状态未变**，
本轮 commit `131613e` 仅修复了缺陷 #1（钱包懒创建链路），**未涉及**会员专属购买门槛的实现，
现象、根因与首轮报告完全一致（`product_membership_rules` 表与 `POST /api/memberships/:id/purchase`
接口仍未落地，购买访问控制仍为纯角色维度）。

按照任务要求，**本次复测不重复根因分析**，该缺陷继续保持"等待产品经理对业务范围做决策"
的状态：是在本阶段补齐实现并重新验收，还是明确调整到后续阶段交付并同步更新验收范围文档。

1. **缺陷 #1【P1】全新用户首次购买触发 HTTP 500 —— 已修复，验证通过 ✅**
   修复方案准确命中根因，未引入任何回归，建议关闭该缺陷工单。

2. **缺陷 #2【P1/设计缺口】"非会员无法购买会员专属应用"业务规则未实现 —— 状态未变，
   仍待产品经理决策**，本轮不重复根因分析（详见首轮报告 `tests/audit-stage1-e2e.md`
   第四节缺陷清单）。建议产品经理尽快明确：
   - 方案 A：在本阶段补齐"会员专属商品访问门槛"实现后重新验收；
   - 方案 B：明确将该能力调整到后续阶段交付，并同步更新 `development-execution-plan.md`
     验收范围文档，避免"验收用例清单与实际交付范围不一致"反复出现。

3. **整体评估**：本阶段已知的 2 个 P1 缺陷中，1 个（缺陷 #1，影响面更广的阻断性问题）
   已修复并验证通过；剩余 1 个（缺陷 #2）是业务规则的实现缺口而非代码缺陷，
   其处理路径取决于产品决策而非技术修复。

**是否允许本阶段合并/上线**：
- 若产品经理评估缺陷 #2（会员专属购买门槛缺失）**不阻断本阶段上线**（即可接受
  "当前仅有会员价格隔离、无强制访问门槛"作为本阶段交付范围，后续阶段再补齐），
  则**建议允许合并上线**——核心业务闭环（注册→实名→充值→购买→扣费→生成流水→
  生成资产、权限即时生效等）已全链路打通且功能正确，唯一已知缺陷属业务规则缺口
  而非阻断性 Bug。
